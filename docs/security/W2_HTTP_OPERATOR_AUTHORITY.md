# W2 HTTP + Operator Authority Contract

Status: candidate security contract for ROT-112 / ROT-45 / ROT-46. This document does not certify production deployment or multi-tenant isolation.

## Supported authority model

The supported release model is **single-operator / single-authority-domain**. The HTTP API authenticates identities and permissions, but the current resource model does not attach tenant ownership metadata to memories, goals, knowledge statements, cells or other resource identifiers.

Therefore:

- this release MUST NOT be represented as tenant-isolated or safe for mutually untrusted users sharing one COS instance;
- cross-tenant ownership isolation is **not certified** because there is no canonical tenant/resource ownership model to enforce;
- adding multi-tenancy requires a separate authority design covering tenant IDs, resource ownership, delegated permissions, query filtering, migration and adversarial cross-tenant tests;
- W2 closes the supported single-authority boundary by making that limitation explicit rather than implying isolation that does not exist.

## Initial operator bootstrap

There is no anonymous HTTP bootstrap route.

A fresh operator provisions an admin credential **locally** on the machine that owns the configured signing key:

1. set `COS_JWT_SECRET` to a cryptographically strong value of at least 32 bytes;
2. run `cos bootstrap-admin <operator-id>` locally;
3. the CLI signs an admin JWT through the canonical `Configuration` + `AuthMiddleware` path;
4. by default the token is written to `~/.cos/operator.jwt` with owner-only mode `0600` (on POSIX systems);
5. use `COS_API_TOKEN_FILE=~/.cos/operator.jwt` for authenticated CLI calls, or paste a token into the browser operator console for the current page lifetime only.

The bootstrap command never calls `/auth/token`, never opens an unauthenticated provisioning endpoint and never prints the token value in normal output.

## CLI credential contract

The deployment HTTP CLI resolves credentials in this order:

1. `COS_API_TOKEN` — explicit ephemeral bearer credential;
2. `COS_API_TOKEN_FILE` — explicit owner-only local credential file;
3. no credential.

Protected calls without a valid credential fail on HTTP 401. Insufficient permissions fail on HTTP 403. Tokens are carried only in the `Authorization: Bearer …` header. Query-string credentials are not supported.

Credential files are rejected on POSIX when group/world permission bits are present. Locally minted tokens are written mode `0600`; their parent directory is created mode `0700` when new.

## Browser credential contract

The built-in `/`, `/dashboard`, `/chat` and `/research` operator pages are same-origin pages generated by the API server.

- the bearer credential exists only in a JavaScript variable after the operator explicitly loads it;
- the token input is `type=password` and is cleared immediately after loading;
- reload/navigation clears the in-memory credential;
- the client uses no `localStorage`, `sessionStorage`, cookie or query-string token;
- protected actions cannot execute until a credential is present;
- 401 clears the in-memory credential and requires re-authentication;
- 403 is surfaced as a permission error without weakening the request;
- server data is rendered using `textContent`, not injected as HTML;
- each page gets a fresh CSP nonce; `connect-src 'self'` constrains API calls to the serving origin;
- the superseded legacy inline HTML clients were removed from the source tree.

## JWT lifetime and revocation

JWT guarantees in the current model:

- HS256 signatures with a strong configured key;
- issuer `cos`, audience `cos-api`, integer `iat`/`exp`, optional `nbf` validation;
- maximum token lifetime: 24 hours;
- expiry is re-evaluated on every authentication;
- rotating `auth.jwtSecret` immediately invalidates JWTs signed by the previous key for that running configuration authority;
- there is **no per-token `jti` denylist or targeted server-side JWT revocation** in this release.

Consequences:

- normal logout is client-side credential deletion;
- compromise requiring server-side revocation must use signing-key rotation, which revokes all JWTs signed by the old key;
- targeted per-token revocation is explicitly out of scope until a durable revocation authority exists.

## API-key rotation and authority

Configured API keys are read from canonical configuration on each authentication attempt. Removing/replacing a key from the live Configuration authority invalidates the old key without recreating `AuthMiddleware`.

API keys currently authenticate as a non-admin user with `read`, `write` and `execute`; they cannot mint admin tokens or read `/config`. This is deliberate: API keys are not the initial admin bootstrap mechanism.

## HTTP request-body boundary

The API body parser is fail-closed:

- default body limit: 1 MiB;
- hard ceiling: 8 MiB even if runtime configuration requests more;
- invalid/negative/non-integer `Content-Length` => 400;
- declared or streamed body above the effective limit => 413;
- malformed JSON => 400;
- JSON body must be an object, not null/array/scalar;
- request stream error/abort => 400;
- protected routes authenticate/authorize before body parsing and service effects;
- internal 5xx responses do not echo exception text;
- error/config responses use `Cache-Control: no-store` where applicable.

## Exposure and production nonclaims

Repository and CI evidence cannot prove which signing keys or API keys were ever deployed. Production exposure remains **UNKNOWN** until an authorized environment inventory is performed. This candidate must not rotate production credentials automatically.

Before any production promotion:

1. inventory deployed `COS_JWT_SECRET` / API-key authorities without copying secret values into GitHub, Linear or logs;
2. determine whether any historical non-cryptographic issuer was used with a real signing value;
3. if exposure is possible, obtain authorization and rotate/invalidate affected keys;
4. re-bootstrap operators and verify protected flows;
5. retain rollback instructions that restore service configuration without restoring a known-compromised credential.

## Acceptance boundary

Passing ROT-112 proves the repository-level single-authority operator/HTTP contract and regression matrix. It does not prove:

- multi-tenant resource isolation;
- production-secret non-exposure;
- per-token targeted JWT revocation;
- public-internet deployment safety;
- global CGEV11 sublime-state verification.
